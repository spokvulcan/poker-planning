# The activity chokepoint owns the clock's precision

**Status:** accepted — decided on [map #253](https://github.com/spokvulcan/poker-planning/issues/253) via [#269](https://github.com/spokvulcan/poker-planning/issues/269). Amends [ADR-0005](0005-room-activity-has-one-model-layer-chokepoint.md). Specified, not yet built.

[ADR-0005](0005-room-activity-has-one-model-layer-chokepoint.md) made `Rooms.updateRoomActivity` the sole writer of `rooms.lastActivityAt` and had every user-initiated model mutation call it. That was the right fix for a poker room, where the writes are sparse and the clock has an exact reader — [ADR-0007](0007-analytics-read-from-a-write-time-snapshot.md)'s freshness check `computedAt >= lastActivityAt`. A retro board breaks the cost assumption without touching the rule. `docs/research/convex-realtime-board.md` §3.2 and §7.2 lay it out: every retro mutation already reads the room row through the permission guard, Convex's OCC conflicts a mutation whose read set was written concurrently (§3.1, verified against the docs), and every member subscribes to `api.rooms.get`, which re-sends its whole result on any change. So a patch on the room row per card move, keystroke batch or dot is simultaneously the hottest write in the room, a conflict for every overlapping retro mutation, and an invalidation of every member's room subscription. [ADR-0016](0016-a-retro-is-one-room-with-its-ceremony-state-beside-it.md) already moved ceremony state off the room row so that no retro write needs to touch it for its own sake; the activity bump was the one reason left.

The research's recommendation was to keep retro writes off the chokepoint and scope ADR-0005 to ephemeral rooms. This ADR takes a narrower cut, because the clock *does* have readers for a retro: the five-day sweep (teamless retros expire, locked at charting), the dashboard's "last active", and whatever quiet-since signal async nudging may want. None of them needs better than day-level precision. So **every retro mutation still calls the chokepoint, and the chokepoint decides how often it writes**: exactly for a poker room, and for a retro room only when the stored clock is more than an hour old. One field, one writer, one sweep query, and the room row is patched at most once an hour per active retro instead of once per write.

## Considered Options

- **Bump on every write, as poker does** (rejected). The problem the ticket describes; research §3.2's hot document and §5's read amplification in one patch.
- **Retro-table writes bypass the chokepoint; the sweep derives a retro candidate's liveness from the newest card, dot and action timestamps** (rejected). Reopens the "derive, don't store" option ADR-0005 rejected, needs three new per-room timestamp indexes, gives `lastActivityAt` two meanings depending on room type, and leaves the dashboard's "last active" with nothing to read.
- **A liveness field on the `retros` row** (rejected). Every member subscribes to that row too (the shared pointer lives on it), so it is the same hot document one table over.
- **Coarse clock inside the existing chokepoint** (chosen). ADR-0005's universal claim stays true; only the write frequency becomes a property of the room type.
- **Coarse clock for poker rooms as well** (rejected). ADR-0007 compares `computedAt` to `lastActivityAt` exactly; a history-changing write that skipped the bump would serve a stale snapshot. Poker stays exact until analytics stops leaning on the clock.

## Consequences

- **`updateRoomActivity` gains a precision rule.** For a room whose `roomType` is `retro`, it writes only if `lastActivityAt` is older than one hour; otherwise it returns without patching. For every other room it writes unconditionally, as today. The chokepoint reads the room to decide, and callers that have just patched the room row anyway (rename, join, leave, role changes, join policy, ratchet) pay nothing extra for the bump landing in the same transaction.
- **ADR-0005's rule is unchanged for callers**: every user-initiated model mutation on a retro-owned row calls the chokepoint — card write, edit, move and delete, cluster form, rename, merge and dissolve, tidy, dot place and remove, advance, walk cursor and coverage, action create, edit, status change and delete. The per-module bump tests in `convex/roomActivity.test.ts` extend to the retro modules, asserting a call rather than a patch.
- **Activity is where the write lands, not where it was issued.** Completing an action from the team page is a user-initiated write to a row the room owns and goes through the chokepoint like any other. It matters only for a teamless retro, whose actions can only be reached from inside the room, but one rule is the point of ADR-0005.
- **Reads and presence are not activity**, as today. Someone sitting on a teamless board reading for six days without writing does not keep it alive; how long a quiet teamless retro survives is the retention window's decision in [#267](https://github.com/spokvulcan/poker-planning/issues/267), together with the sweep's discriminator for retained rooms ([ADR-0008](0008-a-team-is-the-permanent-visibility-boundary.md)).
- **Internal and scheduled writes still never bump**: cascades, sweeps, the cluster centroid or any relayout, and the ratchet's strip of author ids when triggered on a retro at rest — the initiating mutation already did, or there is no user behind it.
- **What "last active" means on a retro.** The dashboard's Retros list and the team page may show `lastActivityAt` and it is accurate to within an hour; nothing may compute a statistic from it. Retro analytics ([#280](https://github.com/spokvulcan/poker-planning/issues/280)) reads card and action timestamps, never the clock.
- **Optimistic updates and single-flighting ([#276](https://github.com/spokvulcan/poker-planning/issues/276))** can assume a retro mutation conflicts on the room row at most once an hour; the remaining contention is on the row being written, which is the row the mutation meant to write.
- **Tests that enforce this**: a retro card write with a fresh clock leaves the room row untouched; the same write with a clock older than an hour patches it; a poker vote patches it every time; a retro room whose only writes in the last five days were card writes survives the sweep; the retro modules each appear in the bump tests; completing an action from the team page calls the chokepoint.
