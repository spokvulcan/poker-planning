One viewer: pages ask it, never Convex's auth booleans

  • src/components/auth/auth-provider.tsx:28-44, 69-96 · in-flight seed
  • src/components/auth/{viewer.ts:30-56, server-viewer.ts:13-22} · in-flight
  • src/app/(app)/room/[roomId]/room-content.tsx:32-40, 121-135
  • src/app/(app)/dashboard/{dashboard-content.tsx:39-55, sessions/sessions-content.tsx:10-16, retros/retros-content.tsx:28-29}
  • src/components/{user-menu/user-menu.tsx:25-37, command-menu/command-menu.tsx:36, 63}
  • convex/model/caller.ts:55-75 · convex/users.ts:9-15 (getGlobalUser)

Problem

The in-flight seed makes the context's two answers disagree by design (the viewer is the server's signedIn while Convex's isAuthenticated is still false), yet 7 decisions in 6 modules read the raw pair, and 4 of 8 test fakes derive one from the other, so no test can show the gap.

Solution

The viewer module owns both meanings, who the page shows and when caller-scoped reads may open, and pages open those reads through it; then one Convex query answers the viewer as caller.ts sees the caller, so the layout's read and the browser's subscription become two adapters that derive nothing.

Wins

  • Interface shrinks: 4 fields → 2
  • Locality: 7 raw-pair decisions → 0
  • Tests fake one shape, seed included
  • “Guest” answered where the server decides
Reopens a documented rule, not an ADR. The second step drops the row-only viewer (docs/authentication.md:386, held by auth-provider.test.tsx:213), which exists because the browser's isAnonymous reads false while loading; the token claim the server reads has no such window. Weigh the seed's own cost too: a Convex round-trip on every signed-in (app) render, blog included.

Let the step rule judge a stack by every sticky it groups

Problem

The step rule takes mine already worked out, so 8 call sites in 4 modules decide which stickies count, and the 3 stack checks look at 2 stickies while Topics.stack moves a root's whole stack: in Write, the stack's author can regroup a colleague's face-down sticky.

04 Worth exploring mock · React Flow in-flight whiteboard · browser

Let the whiteboard own the view: fit, zoom, centre, bring into view

Problem

The whiteboard says it owns fitting and following, yet the chrome's Fit button and the retro's bring-into-view drive React Flow's viewport themselves: two fit rules (the button zooms past the board's 100% cap), and a new sticky measured against the window, not the pane a docked panel narrows.

  • Chrome renders without React Flow
  • Tests: the view, once, at the whiteboard
Half-built in the working tree: FIT_VIEW_OPTIONS, the fitView prop and three “the view” tests are this seam. The whiteboard was judged deep on 4 Oct; this adds actions its callers already need and keeps its shape.

Problem

Within ADR-0006, which names this trigger: the round's call “becomes a registry dispatch” once GitHub has an equivalent effect, and spec 07 §7.5 is that effect. 09 Worth exploring local-substitutable · convex-test guards · server

Close the permission guard's second door, and hold room reads to the scan

  • convex/model/auth.ts:28-45, 118-135 (requireRoomMember, requireCanForUser)

Problem

Since #406 every permission check enters through the room-scoped step but one: the Jira import re-reads a userId through requireCanForUser, then admits each issue with no step; and the scan that holds writes to the step lists 9 files by hand while reads are held only by per-query lists, so issues.list and issues.getCurrent still take no guard.
