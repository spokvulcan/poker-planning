Problem

requireRoomReader reads the room row beside the membership and returns it, so the row joins the read set of all six queries it guards though five discard it; the read only served the Team disjunction (#287) that ADR-0026 removed. Since f06e4fb moved getCanvasNodes onto it, each poker vote re-runs every member's canvas query (every node, note bodies up to 10,000 characters), and retro step and spotlight patches re-run votesCast, actionItems and the retro's canvas list.

Solution

The room access guard decides from identity and membership alone, and retro.board, the one caller that uses the room, reads it itself. This refines "guards return what handlers re-read": a guard's reads join every caller's subscription, so returning the room is free for a mutation but costs a query a subscription edge.

Wins

  • Interface shrinks: one field, one error
  • Poker vote stops re-running getCanvasNodes
  • Locality: retro.board reads its own room
  • Guard's read cost visible where defined
  • Tests pin access from membership alone
Contradicts ADR-0009, but worth reopening because its status line's "returns the room and never a membership" (docs/adr/0009-…md:3) records a return that only carried the Team disjunction, and ADR-0026:33 removed that. The decision itself stands: two guards, never a membership, each read picks one. The same wording needs the same narrow edit in CONTEXT.md:30 and docs/authentication.md:105.
What is proven: a server re-run per member, because the guard reads the auth identity so members don't share a result, and each re-run reads every canvasNodes row. The issue exports gain nothing: getForEnhancedExport is a one-shot convex.query (useIssuesExport.ts:30), and no src code calls getForExport.
Retires an error mode: "Room not found" (requireRoomReader.test.ts:77–86) goes, and a membership that outlived its room would get "You don't have access to this room" instead. That state is unreachable, because the cascade deletes memberships before the room row (model/roomAggregate.ts:24, 151, 161), and no src code matches either string. One verifier rated this Worth exploring because it narrows the interface rather than concentrating behaviour. Problem

No module guarantees that a signed-in caller who writes has a users row of the right kind. Three paths insert one (the client bootstrap's ensureGlobalUser, join, the BetterAuth create hook) and linkAccount repurposes one. Only two of the four set the kind, and rooms.create assumes a row that only the client makes (48fe7e3). The kind is answered four ways, and "a guest's sign-out deletes it" lives in useSignOut, while the server's deleteUser applies no rule.

Solution

One server module answers who is calling. Every guard resolves the caller through it, but only the global ways in (create, join, editGlobalUser, sign-out) may make a row, taking kind, email and name from the session token. It is the only place a row turns permanent, and it asks ownership to retain the rooms. Sign-out becomes a server act that deletes only a guest, Delete account stays its own act, and the client reads the one kind field.

Wins

  • Locality: row birth and kind, one module
  • Interface shrinks: ensureGlobalUser, requireAuthAs go
  • Guest sign-out rule crosses to server
  • Tests cross one seam: convex-test withIdentity
  • Client bootstrap shrinks to token readiness
Bug behind this seam: a deleted account comes back as the wrong kind. Delete account removes only the users row and keeps the BetterAuth user (accountLifecycle.ts:49–52, useDeleteAccount.ts:13), so the create hook never runs for that person again (auth.ts:71–77). When they sign back in, their first create remakes the row through ensureGlobalUser with a guest name and no accountType (model/users.ts:44–51). The retro page then promises "Kept on your account", because of the session fallback (auth-provider.tsx:91, create-content.tsx:151), but ownership.ts:24 won't retain that retro. Before that first write, a Google or magic-link return has no bootstrap at all (signin-form.tsx:54–97), so NavUser shows a skeleton (nav-user.tsx:52–65).
Consistent with ADR-0029 and ADR-0030. accountLifecycle keeps the row's end and the fold, and a row turning permanent already has a hook in Ownership.ownerTurnedPermanent (accountLifecycle.ts:86).
Constraints: the authUserId argument on join and ensureGlobalUser has to stay accepted, and be ignored, while older browsers still send it (users.ts:65,183; model/auth.ts:42–46). So the deletion test's "they vanish" is staged, not immediate. Queries and actions can't insert, so rooms.get, analytics and the Jira preamble keep a lookup; changing them is a tidy-up, not leverage. Nobody has checked at runtime whether isAnonymous reaches getUserIdentity. The token carries every user field except id and image (@convex-dev/better-auth/dist/plugins/convex/index.js:59–61). If the claim doesn't come through, this module shrinks to row birth alone.

Problem
